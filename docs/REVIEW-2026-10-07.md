## Confirmed findings

### Major

#### Routing gives up at 6 routing columns, so an 8-bit adder cannot be built

*core-compiler, crates/redfab-core/src/build.rs:25*

`MAX_ROUTING_COLS = 6` is a hard ceiling in `place_and_route` (build.rs:493-503). Ordinary designs with more than about a dozen inputs need more vertical room between the input column and the first gate column than six routing columns give, and the build fails with "routing failed even with 6 routing columns: routing did not converge".

**Evidence:** Confirmed by running the release CLI: an 8-bit ripple-carry adder (`assign {cout,sum} = a + b + cin`, 102 cells, 17 inputs) fails after 94 s; a 12-bit adder fails after 259 s; a 70-input OR tree fails. In a scratch copy of the crates with the constant raised to 16, the same adder8 mapped.json routes at 7 routing columns (161 x 98 tiles, 57,067 blocks) in 108 s. By contrast mul4 (123 cells, 8 inputs) and counter8 (52 cells) route at 6, so the limit is input/net count across one gap, not cell count. The gate only exercises designs up to 49 cells and 9 inputs (adder4), and `pnr-random` draws 1-6 inputs (pnrtest.rs:25) and up to 40 gates (main.rs:301).

**Impact:** A user who types a textbook 8-bit adder gets a routing failure after a minute and a half; the playground's advertised limits (400 cells, 80,000 blocks in compile.js:6-12) are unreachable. This is the first thing a visitor to a public site will hit.

**Suggested fix:** Make the routing-column count adaptive instead of capped: estimate the columns needed from the number of nets that must cross between each pair of gate columns (the placer already computes spans in place.rs:118-140), start there, and keep growing until routing succeeds or a stated size budget is exceeded. Add adder8 (or a 16-input random netlist family) to `pnr-random` and the DESIGNS list so the gate covers it.

#### Compile time is dominated by failed routing attempts; mid-size designs exceed the browser's 90 s limit

*core-compiler, crates/redfab-core/src/route.rs:68*

Each routing attempt runs up to `MAX_ITERATIONS = 80` PathFinder rounds, and `place_and_route` tries 1, 2, ... routing columns in turn, so a design that needs 6 columns pays for five full failures first. The whole build of mul4 takes 76 s natively in release, 59 s of which is place-and-route; the WebAssembly core in the playground is slower than native and is killed at 90 s (compile.js:11).

**Evidence:** Measured: `redfab layout` (place+route only) on mul4's mapped.json: 58.7 s; `redfab extract`: 3.9 s; one burnout stress walk: 1.8 s; full `redfab build` from mapped.json: 75.9 s. adder4 builds in 14.3 s native and, per PLAN.md stage 10, about 14 s in the browser (its all-pairs timing dominates there). adder12 spent 259 s before reporting failure, so in the browser a too-big design shows up as a timeout, not as a size message.

**Impact:** Designs of roughly 100 cells time out in the playground even when they would route; the user gets "compile took too long" with no hint that a smaller design would work. The practical ceiling today is about 50-120 cells, not the 400 the limits imply.

**Suggested fix:** Start routing at an estimated column count (see the previous finding), stop a PathFinder run early when the overuse count stops falling for N rounds, reuse the previous attempt's history costs when adding a column, and report the real limits (cells, inputs) in the playground and README. Consider lowering the 4^n all-pairs cap (`EXACT_MAX_INPUTS = 10`, timing.rs:152) in the browser or making it optional.

**Verifier's correction:** The retry structure and the 75% share of compile time spent on failed routing attempts are confirmed (route.rs:68/453, build.rs:25/495), and the 90 s deadline covers the whole compile with no size hint (app.js:93-97). However, mul4 (123 cells) did finish under the limit through the WebAssembly pipeline on this machine (74.1 s vs 70.9 s native, about 5% slower), so "mid-size designs exceed the 90 s limit" is borderline rather than certain for mul4 specifically. The stronger, verified problem is adder8 (102 cells): it cannot be routed at all with 6 columns and takes 85.8 s to say so natively, so in the browser it shows up as a timeout. The practical ceiling is set by both the router's 6-column cap and the compile time, roughly 100-120 cells for combinational designs.

#### The supported SystemVerilog subset is undocumented and several refusals are raw Yosys internals, some only after a full place-and-route

*core-compiler, crates/redfab-core/src/synth.rs:8*

Nothing in playground/README.md, index.html or docs tells a user what is accepted (one clock input that feeds nothing else; synchronous reset and enable only; no latches, async reset, memories, tristate, inout, $display, immediate assert; no derived or gated clocks). The map and equiv scripts have no `memory` pass, and clock-shape rules are checked in `clock_input`, which runs inside `analyze_timing` (build.rs:460) only after placement and routing (build.rs:146).

**Evidence:** Battery of 31 constructs built with the debug CLI. Clear refusals: `always_latch` ("D latches are not supported"), async reset ("dffs with async set or reset are not supported"), two clocks, gated clock, ripple clock, clock as output (all "timing: ..." messages after routing). Confusing refusals: a memory array fails in the *proof* with "Gold module contains memories or processes. Run 'memory'"; tristate and inout fail in the proof with "No SAT model available for cell $0_gold ($tribuf)"; `$display` gives "cell $1 has type $print, which is not in the tile library"; an immediate `assert` inside always_ff makes mapped.v unparsable in the proof ("Can't resolve task name `\assert'"); an `always_comb` with a missing else gives "the netlist has a combinational loop". Working: hierarchy (read_slang flattens; mapped.json has one module), parameters, generate, enable FF, negedge FF, initial values, signed multiply, division, Verilog-2001 syntax, unused inputs, zero-input designs.

**Impact:** Users cannot tell in advance what will compile, and the common idioms (async reset, a small RAM, $display in a testbench-style module) fail with messages that point at Yosys passes rather than at the design. Clock-shape problems are only reported after waiting for routing.

**Suggested fix:** Write a short 'what compiles' list in playground/README.md and a root README (none exists). Call `clock_input` right after `Netlist::from_yosys_json`, before placement. Add `memory` (memory_map) to both scripts so arrays become flip-flops and muxes. Translate the known Yosys messages ($tribuf, $print, $mem, $_DLATCH_, async reset, assert) into one-line explanations in compile.js and the CLI.

**Verifier's correction:** Two refinements, neither in the reviewer's favour: (1) the clock-shape refusals are not just late, they are mislabelled: build_netlist (build.rs:123-129) wraps them as "the layout does not implement the netlist:" followed by "timing: ...", so a two-clock design is reported as a layout defect. (2) The "only after waiting for routing" cost is small for small designs (about 2 s end to end in my runs); it grows with design size and matters most against the playground's 90 s compile limit (playground/compile.js:11).

#### The practical design size is far below the advertised limits, and the page shows no progress while the core works

*playground, playground/compile.js:8*

LIMITS says 400 cells / 80,000 blocks / 90 s, but the core's placing, routing and timing check is what consumes the time: a 4x4 multiplier (123 cells) takes 78 s in the browser, an 8-bit adder fails to route after 74 s, and a 48-bit shift register fails to route after 37 s. During that time the status is just 'Compiling…' and the log's last line is 'placing, routing and checking' because the core's build is one synchronous call.

#### Observer-stream reconnect loop grows exponentially: the backend destroys itself within ~12 s of Minecraft dying or the stream dropping

*live-backend-and-mod, server/minecraft.mjs:84*

#### A controller can flood the shared RCON queue with lever changes and delay every other plot's clock and levers

*live-backend-and-mod, server/plots.mjs:222*

## 3. The "Later" items (`PLAN.md:374-375`)

Recommended order and why:

1. **Compaction pass** (not in the Later list but it gates two of them; 20-40 h). Every Later item is bounded by area and period: adder4 is 365 x 250 at 3x the predicted density (PLAN.md:169), counter4's period is 132 ticks from long feedbacks (PLAN.md:228). DESIGN.md:203 already sets the rule: every compaction move is followed by re-extraction and LVS, so the safety story survives. Concrete moves: shorten feeds by placing cells nearer their sinks, share the clock trunk, drop repeaters where strength allows (the router knows exact strengths, `weak_signals` checks them), and let gate columns pack more than one cell per row when nets allow. Measure with the shipped designs and `pnr-random`; the target is adder4 under 256 x 256 and counter4 under 100 ticks.

2. **On-board clock generator** (10-15 h). Removes the backend and the player from the timing path (findings "clock driven from userland over RCON", "input window enforced only by the harness"). A repeater ring oscillator tile whose period is a multiple of the design's reported `period`, with a lever as enable; the timing analysis already knows the period, so the generator's setting is derived, not chosen. Needs: a new tile with its own recorded trace in both modes (the stage 5 procedure), an `oscillator` input kind in `design.json`, and the harness/backend treating the clock as internal. Do it before the ALU because the ALU's benchmark is meaningless if a human drives the clock.

3. **8-bit ALU with speed benchmark** (depends on §1.4B and item 1; 10-20 h of design work once they land). This is DESIGN.md M4 (`:445`): "congestion, long wires, glitch burnout, runtime; time it here". It is the first design that exercises the burnout budget at a real clock (DESIGN.md:80), so expect `input_spacing`/period to bind. Deliverable: `designs/alu8`, cycles-vanilla in the game, a table of period and settle vs. operation.

4. **Register-file and ROM generators** (15-25 h). DESIGN.md:162 and M5: parametric generators that emit a tile-aligned template plus a timing model plus a Verilog model, OpenRAM-style, rather than synthesizing `reg [7:0] mem[0:15]` through NOR gates (which §1.3's `memory` pass does, but at 57 cells for 2x4 bits it will never scale). This needs fixed-block placement in `place.rs` (a cell with a footprint larger than one tile that the placer treats as opaque) and a macro timing model in `timing.rs`. The §10 decision 3 (comparators and copper bulbs, "revisit later for ROM and counter density") belongs here: a comparator-based ROM is far denser but makes strength analog; decide after the NOR version is measured.

5. **`.litematic` / `.schem` export** (3-5 h). Cheap and nearly free of risk (DESIGN.md:235 chose the World index order to match Litematica's), but low value until someone actually opens the `.nbt` in a client. Do the one-hour experiment first: a 26.3 client with Litematica 0.29.1 on nor2 and counter4, screenshot into `docs/`. If `.nbt` loads, `.litematic` export is a nicety; if it does not, this item jumps to the top. Either way it fixes the "claimed as fact but never tried" finding.

6. **Tiny CPU** (open-ended; 40+ h after 1-4). The showcase. DESIGN.md:141 warns it needs stacked planes and that a large paste is slow; it only makes sense after the compaction pass and the generators exist. Scope it as the smallest thing that runs a loop: 4-bit data path, 16-word ROM program, two registers, the ALU, a program counter; the on-board clock at whatever period the analysis gives (DESIGN.md:140 predicts 0.1-0.5 Hz).

Reasoning for the order: 1 and 2 raise the ceiling for everything else and fix today's correctness-adjacent weakness (the external clock); 3 is the first design that stresses the whole toolchain and produces a number to show; 4 is needed by 6 and benefits from 3's measurements; 5 is a quick experiment that can be slotted anywhere; 6 is the reward.

## 4. Language coverage implied by the sweep

The sweep (24 fresh designs, 15 compiled and all correct, 9 refused) says the subset that works is wider than the docs admit and the subset that is refused is refused for three different reasons. Work items, beyond §1.2 and §1.3:

1. **Pin what works with checks (2-3 h).** Promote `mul2`, `mux4`, `prio3`, `cmp4`, `param_add`, `signed_sub`, `divmod`, `hier`, `lfsr3`, `negedge`, `init_reg` into `designs/` with Verilator cycle/truth checks in `harness.design` and the DESIGNS list in `check`. Today nothing guards parameters, generate, hierarchy, signed arithmetic, division, negedge or `initial`, so a Yosys or script change could silently drop one. `init_reg` also closes the "proof is init-blind and no committed design uses `initial`" finding on the Verilator side; for the proof itself, add an explicit init comparison between gold and the mapped netlist (read both JSONs, compare `init` per state bit) in `main.rs`/`compile.js` (1-2 h), since `equiv_induct` ignores initial state.

2. **Undefined initial values (1 h).** Yosys `opt` folds an un-reset, un-initialised register into a constant or `x` (netlist.rs:73 then refuses "port q is tied to x"). Decide a policy and document it: either `setundef -init -zero` before `opt` so every register starts at 0 like Verilator shows, or keep the fold and map the x-port refusal to "register q is never assigned or has no reset; give it a reset or an `initial` value".

3. **Memories as logic (after §1.3).** Document that `reg [W-1:0] mem[N]` becomes flip-flops and muxes and what size still routes (measure: 2x2 builds, 2x4 does not route at HEAD). The generator in §3.4 is the real answer.

4. **Async reset: refuse or support?** Refused clearly today (`dfflegalize`, synth.rs:14). Supporting it needs a DFF tile with an asynchronous clear path and its own characterization (stage 8 procedure, 8-15 h). Most hobby Verilog uses `posedge clk or posedge rst`, so this is the single most common refusal a stranger will hit; the cheap step is §1.2's message that shows the synchronous form. Decide after seeing real users' sources.

5. **Multiple clocks, gated and derived clocks, latches, tristate, `$display`.** Keep refusing; make the messages say why (§1.2). Clock division (a counter output used as a clock) is the one that users will ask for; it would need the timing analysis to treat a flip-flop output as a clock root, which `analyze_sequential` does not model. Out of scope until the on-board clock exists.

6. **Port widths and names.** `[0:3]`/`[7:4]` ranges mislabel bits (§1.3); escaped identifiers reach `innerHTML` (§1.8). Also decide whether struct/packed-array ports (SystemVerilog `logic [3:0][1:0]`) should be flattened with readable names; read_slang flattens them, naming is the question. 1 h to test and document.

7. **Size feedback before routing (part of §1.4A).** After synthesis the cell count and a cut estimate are known in under a second; tell the user "123 cells; the router handles about N today" before spending 90 s.

Honest effort for §4: 8-12 h without async reset support; 20-25 h with it.
